### F1. Completed compute calls create unbounded, indefinite server-side subscriptions

- **Severity:** HIGH
- **Confidence:** CONFIRMED
- **Category:** dos
- **Location:** `src/ActualLab.Fusion/Client/Internal/RpcInboundComputeCall.cs:83`, `src/ActualLab.Fusion/Client/Internal/RpcInboundComputeCall.cs:90`, `src/ActualLab.Fusion/Configuration/ComputedOptions.cs:32`, `src/ActualLab.Rpc/Infrastructure/RpcCallTrackers.cs:15`, `src/ActualLab.Rpc/Infrastructure/RpcCallTrackers.cs:59`
- **What:** After returning a compute result, the server keeps the inbound call registered until its captured `Computed` invalidates. The default is no automatic invalidation, and the per-peer inbound-call dictionary has no count or age limit.
- **Why it matters / attack path:** A remote peer can repeatedly invoke any exposed compute method with fresh wire-controlled call IDs and leave the connection open without cancelling the calls. A method returning a stable computed value never reaches stage 2 completion, so every request retains an inbound call, cancellation state, continuation/event handler, and a strong reference to the computed graph. An anonymously reachable compute method makes this a pre-authentication memory DoS; otherwise any low-privilege peer that can invoke a compute method can exhaust the server over time.
- **Evidence:** Regular calls call `Unregister()` immediately, but compute calls instead execute `await ProcessStage2(...)` (`src/ActualLab.Fusion/Client/Internal/RpcInboundComputeCall.cs:83-87`). Stage 2 awaits `computed.WhenInvalidated(...)` and unregisters only afterward (`src/ActualLab.Fusion/Client/Internal/RpcInboundComputeCall.cs:90-107`). `AutoInvalidationDelay` defaults to `TimeSpan.MaxValue` (`src/ActualLab.Fusion/Configuration/ComputedOptions.cs:32-33`). The tracker is an unbounded `ConcurrentDictionary` (`src/ActualLab.Rpc/Infrastructure/RpcCallTrackers.cs:15`), and `GetOrRegister` accepts each new ID without a quota (`src/ActualLab.Rpc/Infrastructure/RpcCallTrackers.cs:59-66`).
- **Fix:** Enforce a configurable per-peer limit on result-ready compute subscriptions and reject or evict calls above it. Add a finite post-result lease/idle timeout, and unregister on lease expiry even when the computed remains valid. Consider deduplicating identical subscriptions per peer, but retain a hard count/retained-bytes bound regardless.

### F2. Invalidation replay failures are acknowledged and permanently lose cache invalidations

- **Severity:** HIGH
- **Confidence:** CONFIRMED
- **Category:** logic
- **Location:** `src/ActualLab.Fusion/Operations/Internal/InvalidatingCommandCompletionHandler.cs:151`, `src/ActualLab.Fusion/Operations/Internal/InvalidatingCommandCompletionHandler.cs:164`, `src/ActualLab.Fusion/Operations/Internal/CompletionProducer.cs:34`, `src/ActualLab.Fusion/Operations/OperationCompletionNotifier.cs:55`, `src/ActualLab.Fusion.EntityFramework/Operations/LogProcessing/DbOperationLogReader.cs:29`
- **What:** Exceptions thrown while replaying a committed command in invalidation mode are logged but never propagated. The completion is therefore treated as successful even though one or more computed dependencies were not invalidated; local listener failures are also swallowed and their operation UUID remains marked as processed.
- **Why it matters / attack path:** A client-triggered command can commit successfully and then fail during its invalidation replay because of attacker-influenced stored command data or a transient service/dependency failure. External operation-log delivery sees a successful completion and does not retry. For a local operation, listener errors are swallowed, the UUID remains in the recently-seen set, and the EF log reader deliberately skips rows from the local host. With the default infinite auto-invalidation horizon, authorization or application data cached from before the write can remain stale indefinitely.
- **Evidence:** `TryInvalidate` catches every handler exception, records/logs it, and returns the next index without throwing (`src/ActualLab.Fusion/Operations/Internal/InvalidatingCommandCompletionHandler.cs:151-170`); the outer handler only labels the telemetry outcome as an error (`src/ActualLab.Fusion/Operations/Internal/InvalidatingCommandCompletionHandler.cs:87-100`). `CompletionProducer` rethrows only for external completion errors and merely logs local errors (`src/ActualLab.Fusion/Operations/Internal/CompletionProducer.cs:34-54`). `NotifyCompleted` inserts the UUID before invoking listeners and, on a local failure, logs without removing it (`src/ActualLab.Fusion/Operations/OperationCompletionNotifier.cs:55-60`, `src/ActualLab.Fusion/Operations/OperationCompletionNotifier.cs:93-104`). The durable EF reader returns immediately for local-host rows (`src/ActualLab.Fusion.EntityFramework/Operations/LogProcessing/DbOperationLogReader.cs:29-34`).
- **Fix:** Continue attempting all replay handlers, then throw an aggregate error if any failed so external readers redeliver the operation. For committed local operations, keep the client-visible commit successful but durably enqueue or expose the failed completion for retry, remove its recently-seen marker on failure, and let the local log reader retry it until invalidation succeeds.

### F3. The shared remote cache crosses service-provider and server trust boundaries

- **Severity:** HIGH
- **Confidence:** CONFIRMED
- **Category:** info-leak
- **Location:** `src/ActualLab.Fusion/Client/Caching/SharedRemoteComputedCache.cs:12`, `src/ActualLab.Fusion/Client/Caching/SharedRemoteComputedCache.cs:16`, `src/ActualLab.Fusion/FusionBuilder.cs:454`, `src/ActualLab.Rpc/Caching/RpcCacheKey.cs:22`, `src/ActualLab.Fusion/Client/Interception/RemoteComputeMethodFunction.cs:283`, `src/ActualLab.Fusion/Client/Interception/RemoteComputeMethodFunction.cs:462`
- **What:** `SharedRemoteComputedCache` stores the first constructed cache in a process-global static property, so all later Fusion service providers silently use that same instance. Its cache key contains only the RPC method name and serialized arguments, with no peer, server endpoint, hub, service-provider, tenant, or authentication namespace.
- **Why it matters / attack path:** In a process that creates Fusion providers for two backends using the same RPC contract, a hostile or lower-trust server can return a cacheable value for a method/argument pair. A later call through the trusted provider finds the hostile server's entry and returns it immediately before background RPC validation. In the opposite direction, a provider connected to the hostile server can observe a cached value populated from the trusted backend. The public `AddSharedRemoteComputedCache` helper creates this configuration directly; construction order decides which provider's cache every provider receives.
- **Evidence:** `Instance` is static, and the constructor uses unsynchronized first-writer-wins initialization (`src/ActualLab.Fusion/Client/Caching/SharedRemoteComputedCache.cs:12-18`); every operation delegates to that instance (`src/ActualLab.Fusion/Client/Caching/SharedRemoteComputedCache.cs:20-32`). `AddSharedRemoteComputedCache` registers a provider-local `TCache` but wraps it with the global holder (`src/ActualLab.Fusion/FusionBuilder.cs:454-469`). `RpcCacheKey` consists only of `Name` and `ArgumentData` (`src/ActualLab.Rpc/Caching/RpcCacheKey.cs:22-33`). A hit is deserialized into a `RemoteComputed` and returned immediately (`src/ActualLab.Fusion/Client/Interception/RemoteComputeMethodFunction.cs:283-303`), while server results are stored under that unnamespaced key (`src/ActualLab.Fusion/Client/Interception/RemoteComputeMethodFunction.cs:462-484`).
- **Fix:** Replace the mutable process-global static with an explicitly supplied shared-cache object whose sharing scope is controlled by the application. Namespace every key by a stable server/route identity plus any tenant, session, or security context on which the result depends. At minimum, partition by `RpcHub`/provider and endpoint, and make initialization thread-safe.

### F4. An invalidated-in-flight computation is briefly published as consistent

- **Severity:** MEDIUM
- **Confidence:** CONFIRMED
- **Category:** race
- **Location:** `src/ActualLab.Fusion/Computed.cs:274`, `src/ActualLab.Fusion/Computed.cs:371`, `src/ActualLab.Fusion/Internal/ComputedImpl.Helpers.cs:19`
- **What:** Invalidation during computation sets an `InvalidateOnSetOutput` flag, but `TrySetOutput` subsequently publishes the output with state `Consistent`, releases the lock, and only then invalidates it. Concurrent readers can consume the just-published output even though invalidation happened before publication.
- **Why it matters / attack path:** A write or remote invalidation can race a long-running computation. During the gap after `TrySetOutput` releases the lock and before its follow-up `Invalidate`, another request for the same input takes the lock-free existing-computed fast path and receives a value computed across a known-invalid dependency epoch. The later invalidation makes the defect self-correcting, but the stale value has already escaped and can drive an authorization or data decision for that request.
- **Evidence:** Invalidation in `Computing` state only ORs flags and returns (`src/ActualLab.Fusion/Computed.cs:274-278`). `TrySetOutput` changes the state to `Consistent` and assigns `_output` under the lock, releases the lock, then checks the flag and calls `Invalidate` (`src/ActualLab.Fusion/Computed.cs:371-387`). `TryUseExisting` accepts any object whose visible state is `Consistent` and returns it without taking the computed's lock (`src/ActualLab.Fusion/Internal/ComputedImpl.Helpers.cs:19-32`).
- **Fix:** Do not expose a `Consistent` state when `InvalidateOnSetOutput` is set. Publish the output and transition directly to `Invalidated` (or to a non-consumable transitional state) under the same lock, then perform event propagation and cleanup outside the lock while still allowing the original producer to receive its output.

### F5. Faulted cache lifecycle tasks are treated as success and can resurrect stale entries

- **Severity:** MEDIUM
- **Confidence:** CONFIRMED
- **Category:** logic
- **Location:** `src/ActualLab.Fusion/Client/Caching/RemoteComputedCache.cs:49`, `src/ActualLab.Fusion/Client/Caching/RemoteComputedCache.cs:87`, `src/ActualLab.Fusion/Client/Caching/RemoteComputedCache.cs:103`, `src/ActualLab.Fusion/Client/Caching/FlushingRemoteComputedCache.cs:46`, `src/ActualLab.Fusion/Client/Caching/FlushingRemoteComputedCache.cs:90`, `src/ActualLab.Fusion/Client/Caching/FlushingRemoteComputedCache.cs:112`
- **What:** Cache initialization checks `Task.IsCompleted` rather than successful completion and silently suppresses initialization faults before reading the backing cache. The flushing cache similarly treats a faulted prior flush as complete, replaces the failed queue, and never retries its writes or deletion tombstones.
- **Why it matters / attack path:** If persistent storage fails while clearing a cache after a version change, subsequent requests continue reading entries that the version barrier was meant to make unusable; compatible old payloads are returned as live cached results. Separately, if a queued removal fails to flush, the next flush discards that failed queue. Once it is no longer visible in `FlushingQueue`, `Get` falls through to the backing store and can resurrect the stale value. A hostile server response cached before the storage fault can therefore continue to be served after the client attempted to invalidate or migrate it.
- **Evidence:** A version mismatch calls `Clear` before writing the new version (`src/ActualLab.Fusion/Client/Caching/RemoteComputedCache.cs:49-65`), but `WhenInitializedUnlessVersionKey` returns success for any completed task, including a faulted one (`src/ActualLab.Fusion/Client/Caching/RemoteComputedCache.cs:87-90`), and the read path silently awaits only while initialization is incomplete before proceeding to `Get` (`src/ActualLab.Fusion/Client/Caching/RemoteComputedCache.cs:103-107`). The flushing read path trusts `FlushQueue`/`FlushingQueue` and otherwise fetches persistent data (`src/ActualLab.Fusion/Client/Caching/FlushingRemoteComputedCache.cs:46-54`). `DelayedFlush` suppresses initialization/prior-flush faults (`src/ActualLab.Fusion/Client/Caching/FlushingRemoteComputedCache.cs:90-93`, `src/ActualLab.Fusion/Client/Caching/FlushingRemoteComputedCache.cs:112-131`), then overwrites `FlushingQueue` and starts a new flush (`src/ActualLab.Fusion/Client/Caching/FlushingRemoteComputedCache.cs:133-138`).
- **Fix:** Gate reads and writes on `WhenInitialized.IsCompletedSuccessfully`; on initialization failure, fail the cache closed and surface or convert the error to a cache miss without consulting old storage. Preserve a failed flushing dictionary, merge later mutations into it with correct last-write-wins ordering, and retry with backoff. Do not replace the visible failed queue until its flush succeeds.

### F6. `WhenInvalidated` can leak cancellation registrations and computed graphs

- **Severity:** MEDIUM
- **Confidence:** CONFIRMED
- **Category:** leak
- **Location:** `src/ActualLab.Fusion/Internal/WhenInvalidatedClosure.cs:17`, `src/ActualLab.Fusion/Internal/WhenInvalidatedClosure.cs:27`, `src/ActualLab.Fusion/ComputedExt.cs:114`, `src/ActualLab.Fusion/State/ComputedState.cs:167`
- **What:** `WhenInvalidatedClosure` subscribes to invalidation before creating and storing its cancellation registration. If invalidation wins that constructor race, the handler disposes the field's default value; the constructor then creates a real registration that nothing disposes until the token itself is cancelled.
- **Why it matters / attack path:** Computed-state update loops call `WhenInvalidated` with the long-lived state disposal token. Under concurrent invalidation/recomputation, each race leaves a completed wait registered on that token. The token source retains the closure, which retains the old `Computed`, its input, and potentially its dependency graph, so repeated races grow memory until the entire state is disposed.
- **Evidence:** The constructor adds `_onInvalidatedHandler` at line 22 but assigns `_cancellationTokenRegistration` only at line 24 (`src/ActualLab.Fusion/Internal/WhenInvalidatedClosure.cs:17-25`). `OnInvalidated` disposes whatever value the field currently contains (`src/ActualLab.Fusion/Internal/WhenInvalidatedClosure.cs:27-31`). The public helper creates this closure for every cancellable wait (`src/ActualLab.Fusion/ComputedExt.cs:114-123`), and `ComputedState.UpdateCycle` repeatedly waits with `DisposeToken` (`src/ActualLab.Fusion/State/ComputedState.cs:167-176`).
- **Fix:** Coordinate subscription and registration with a small atomic state machine. After storing the registration, re-check whether completion already won and dispose it if so; likewise ensure cancellation and invalidation each remove the event handler and dispose the registration exactly once.

### F7. Disposed RPC peer monitors remain rooted by an undisposed token registration

- **Severity:** MEDIUM
- **Confidence:** CONFIRMED
- **Category:** leak
- **Location:** `src/ActualLab.Fusion/Extensions/RpcPeerStateMonitor.cs:72`, `src/ActualLab.Fusion/Extensions/RpcPeerStateMonitor.cs:147`, `src/ActualLab.Fusion/State/ComputedState.cs:114`, `src/ActualLab.Core/Net/RetryDelayer.cs:27`
- **What:** Each `ComputeLastReconnectDelayCancelledAtState` computation registers its `Computed` on the reconnect delayer's cancellation token and discards the returned `CancellationTokenRegistration`. Disposing the monitor disposes its states but does not remove that registration or invalidate the current computed.
- **Why it matters / attack path:** Scoped clients can create and dispose `RpcPeerStateMonitor` instances repeatedly. The hub-owned retry delayer's still-live token roots the registered computed; the computed's `State` input and bound computer delegate retain the monitor and its scoped service graph. Unless some external code eventually calls `CancelDelays`, every disposed scope can remain live for the lifetime of the hub.
- **Evidence:** The registration returned by `CancelDelaysToken.Register(...)` is ignored (`src/ActualLab.Fusion/Extensions/RpcPeerStateMonitor.cs:147-157`). `DisposeAsyncCore` only disposes the two states (`src/ActualLab.Fusion/Extensions/RpcPeerStateMonitor.cs:72-78`). `ComputedState.Dispose` cancels its update token but does not invalidate the current computed or unregister callbacks held by unrelated tokens (`src/ActualLab.Fusion/State/ComputedState.cs:114-131`). `RetryDelayer.CancelDelaysToken` is backed by a CTS that remains live until `CancelDelays` replaces it (`src/ActualLab.Core/Net/RetryDelayer.cs:27-31`, `src/ActualLab.Core/Net/RetryDelayer.cs:59-66`).
- **Fix:** Store the registration on the monitor, atomically replace/dispose it on recomputation, and dispose it in `DisposeAsyncCore`. Alternatively, register a callback tied to the state/monitor disposal token so the reconnect-token registration is removed as soon as the state is disposed.

### F8. Whole-chain invalidation tracking can create a self-cycle and spin forever

- **Severity:** MEDIUM
- **Confidence:** PLAUSIBLE
- **Category:** dos
- **Location:** `src/ActualLab.Fusion/Computed.cs:496`, `src/ActualLab.Fusion/Computed.cs:502`, `src/ActualLab.Fusion/InvalidationSource.cs:35`, `src/ActualLab.Fusion/InvalidationSource.cs:68`, `src/ActualLab.Fusion/ComputedExt.cs:105`, `src/ActualLab.Fusion/Diagnostics/FusionMonitor.cs:211`
- **What:** If a dependency invalidates during the `AddDependency`/`AddDependant` race, `AddDependant` invalidates the dependant with the dependant itself as its source. In `WholeChain` mode this stores a self-referential invalidation source, while both origin walkers have no cycle detection.
- **Why it matters / attack path:** With optional whole-chain tracking enabled, concurrent application or remote invalidation can hit the window where a computation tries to attach to an already-invalidated dependency. When a `FusionMonitor` observes unregistration, it synchronously follows the invalidation origin forever. This can wedge the invalidating thread and the monitor's statistics lock. The exact race was proven from the source, but not reproduced under runtime scheduling, so confidence is `PLAUSIBLE`.
- **Evidence:** `AddDependency` calls `dependency.AddDependant(this)` (`src/ActualLab.Fusion/Computed.cs:496-498`). The invalidated case calls `dependant.Invalidate(..., new InvalidationSource(dependant))` rather than naming the dependency (`src/ActualLab.Fusion/Computed.cs:502-510`). The `Computed` constructor preserves the object itself in `WholeChain` mode (`src/ActualLab.Fusion/InvalidationSource.cs:68-71`). `InvalidationSource.Origin` and `GetInvalidationOrigin` both follow links in unbounded loops without a visited set (`src/ActualLab.Fusion/InvalidationSource.cs:35-46`, `src/ActualLab.Fusion/ComputedExt.cs:105-109`), and the monitor invokes the latter synchronously during unregistration (`src/ActualLab.Fusion/Diagnostics/FusionMonitor.cs:211-218`).
- **Fix:** At `src/ActualLab.Fusion/Computed.cs:509`, use the invalidated dependency (`this`) as the source, not the dependant. Defensively add identity-cycle detection or a bounded traversal to both invalidation-origin walkers so malformed chains cannot wedge diagnostics.
