### F1. Raw key-value storage is exposed as a frontend RPC service

- **Severity:** CRITICAL
- **Confidence:** CONFIRMED
- **Category:** auth-bypass
- **Location:** `src/ActualLab.Fusion.Ext.Services/Extensions/FusionBuilderExt.cs:38`, `src/ActualLab.Fusion.Ext.Services/Extensions/FusionBuilderExt.cs:66`, `src/ActualLab.Fusion.Ext.Services/Extensions/IKeyValueStore.cs:8`, `src/ActualLab.Fusion.Ext.Services/Extensions/IKeyValueStore.cs:15`, `src/ActualLab.Fusion.Ext.Services/Extensions/Services/SandboxedKeyValueStore.cs:74`
- **What:** Both storage providers register the unrestricted `IKeyValueStore` with `FusionBuilder.AddService`, although the interface is not marked as a backend service. Its frontend-visible compute methods accept an arbitrary shard and key or prefix, completely bypassing `ISandboxedKeyValueStore`'s session/user prefix checks.
- **Why it matters / attack path:** On a server whose Fusion default service mode exposes registered services, an unauthenticated RPC peer can invoke `IKeyValueStore.ListKeySuffixes(shard, "", pageRef)`, enumerate every stored key in that shard, and invoke `Get(shard, key)` for each result. This crosses every session and user namespace that `SandboxedKeyValueStore` is intended to isolate; in a sharded application it also lets the peer select any configured shard. No generated client is needed because service and method names are attacker-controlled in the RPC threat model.
- **Evidence:** `AddInMemoryKeyValueStore` and `AddDbKeyValueStore` call `fusion.AddService<IKeyValueStore, ...>()` at `src/ActualLab.Fusion.Ext.Services/Extensions/FusionBuilderExt.cs:38` and `src/ActualLab.Fusion.Ext.Services/Extensions/FusionBuilderExt.cs:66`. `IKeyValueStore` inherits only `IComputeService` at `src/ActualLab.Fusion.Ext.Services/Extensions/IKeyValueStore.cs:8`; its `Get`, `Count`, and `ListKeySuffixes` methods accept raw shard/key inputs at `src/ActualLab.Fusion.Ext.Services/Extensions/IKeyValueStore.cs:15`. In contrast, the intended facade obtains a `KeyChecker`, validates the caller's key, and only then delegates at `src/ActualLab.Fusion.Ext.Services/Extensions/Services/SandboxedKeyValueStore.cs:74`. Marking only `KeyValueStore_Set` and `KeyValueStore_Remove` as backend commands does not hide the read methods.
- **Fix:** Register `IKeyValueStore` as a local compute service rather than an RPC service, or mark the entire raw interface as backend-only and keep backend exposure disabled on public endpoints. Expose only `ISandboxedKeyValueStore` to frontend peers. Add a service-registry regression test proving the raw service and all of its methods are absent from a frontend peer.

### F2. Unknown session shard tags grow permanent per-shard caches

- **Severity:** HIGH
- **Confidence:** CONFIRMED
- **Category:** dos
- **Location:** `src/ActualLab.Fusion.EntityFramework/Sharding/DbShardResolver.cs:51`, `src/ActualLab.Fusion.EntityFramework/Sharding/DbShard.cs:11`, `src/ActualLab.Fusion.EntityFramework/DbEntityResolver.cs:151`, `src/ActualLab.Fusion.EntityFramework/DbEntityResolver.cs:281`, `src/ActualLab.Fusion.EntityFramework/Sharding/ShardDbContextFactory.cs:149`
- **What:** In a multi-shard deployment, the default resolver accepts any non-special session shard tag without checking registry membership. Entity and context resolvers insert attacker-selected shard strings into singleton dictionaries before the context factory eventually rejects an unknown shard, and the failed entries are not evicted.
- **Why it matters / attack path:** An unauthenticated peer repeatedly calls the public `IAuth.GetSessionInfo` query with valid-looking sessions such as `abcdefgh&s=unique-1`, `abcdefgh&s=unique-2`, and so on. `DbAuthService` resolves each tag and asks the session entity resolver for the row. Every unique value creates a retained `BatchProcessor`; its attempted database access also creates a retained context-factory `CacheEntry` before failing with “Shard doesn't exist.” Repetition causes unbounded process memory and worker-state growth without requiring a valid account or a configured shard.
- **Evidence:** `DbShardResolver.Resolve` returns `DbShard.Validate(session.GetTag(SessionShardTag))` at `src/ActualLab.Fusion.EntityFramework/Sharding/DbShardResolver.cs:58`, while the default validator merely rejects special names at `src/ActualLab.Fusion.EntityFramework/Sharding/DbShard.cs:11`. `DbEntityResolver.Get` calls `GetBatchProcessor` at `src/ActualLab.Fusion.EntityFramework/DbEntityResolver.cs:151`, whose dictionary performs `GetOrAdd(shard, ...)` at `src/ActualLab.Fusion.EntityFramework/DbEntityResolver.cs:287` and is cleared only when the singleton is disposed. The context factory likewise performs `_factories.GetOrAdd` at `src/ActualLab.Fusion.EntityFramework/Sharding/ShardDbContextFactory.cs:156`; registry membership is checked later at `src/ActualLab.Fusion.EntityFramework/Sharding/ShardDbContextFactory.cs:170`, and initialization failure only clears the entry's `_whenInitialized` field at `src/ActualLab.Fusion.EntityFramework/Sharding/ShardDbContextFactory.cs:347`, not the dictionary entry.
- **Fix:** Make `DbShardResolver.Resolve` reject values for which `ShardRegistry.CanUse` is false before returning them. Independently validate before both resolver dictionaries call `GetOrAdd`, and remove a context-factory `CacheEntry` when initialization fails. Add a test that sends many unknown shard tags and asserts both caches remain bounded/empty.

### F3. Signing out a nonexistent session creates a persistent session row

- **Severity:** HIGH
- **Confidence:** CONFIRMED
- **Category:** dos
- **Location:** `src/ActualLab.Fusion.Ext.Contracts/Authentication/IAuth.cs:12`, `src/ActualLab.Fusion.Ext.Services/Authentication/Services/DbAuthService.cs:36`, `src/ActualLab.Fusion.Ext.Services/Authentication/Services/DbAuthService.cs:84`, `src/ActualLab.Fusion.Ext.Services/Authentication/Services/DbSessionInfoRepo.cs:61`
- **What:** The public sign-out command uses `Sessions.GetOrCreate` even when the supplied session has never existed. Thus a nominally idempotent logout operation inserts and updates a database row for every new attacker-selected session ID.
- **Why it matters / attack path:** A pre-authentication RPC peer submits `Auth_SignOut` commands containing distinct syntactically valid session IDs. Each call creates a `_Sessions` row and produces the associated operation-log work. The default trimmer retains such rows for up to 60 days, so a sustained low-cost command stream can grow the session table, indexes, and operation log until database capacity or throughput is exhausted.
- **Evidence:** `IAuth.SignOut` is a frontend command at `src/ActualLab.Fusion.Ext.Contracts/Authentication/IAuth.cs:12`. Its database implementation only applies `RequireValid` at `src/ActualLab.Fusion.Ext.Services/Authentication/Services/DbAuthService.cs:39`, then calls `Sessions.GetOrCreate` at `src/ActualLab.Fusion.Ext.Services/Authentication/Services/DbAuthService.cs:84`. For a miss, that repository constructs a new `SessionInfo`, calls `dbContext.Add`, and saves it at `src/ActualLab.Fusion.Ext.Services/Authentication/Services/DbSessionInfoRepo.cs:64`. The default cleanup age is 60 days at `src/ActualLab.Fusion.Ext.Services/Authentication/Services/DbSessionInfoTrimmer.cs:30`.
- **Fix:** Sign-out must query an existing row with an update lock and return immediately when it is absent; it must never call a create-or-upsert path for a missing session. Add a regression test that signs out many unknown sessions and verifies that the session table remains empty.

### F4. Anonymous sandboxed writes have no storage quota or size bound

- **Severity:** HIGH
- **Confidence:** CONFIRMED
- **Category:** dos
- **Location:** `src/ActualLab.Fusion.Ext.Contracts/Extensions/ISandboxedKeyValueStore.cs:11`, `src/ActualLab.Fusion.Ext.Services/Extensions/Services/SandboxedKeyValueStore.cs:39`, `src/ActualLab.Fusion.Ext.Services/Extensions/Services/SandboxedKeyValueStore.cs:103`, `src/ActualLab.Fusion.Ext.Services/Extensions/Services/DbKeyValueStore.cs:21`, `src/ActualLab.Fusion.Ext.Services/Extensions/Services/DbKeyValue.cs:14`
- **What:** `ISandboxedKeyValueStore.Set` is available before authentication, and the sandbox limits only the key prefix and expiration time. It imposes no per-session key count, aggregate byte quota, item/batch limit, or value-size limit before persisting the data.
- **Why it matters / attack path:** An unauthenticated peer obtains or supplies valid anonymous sessions and repeatedly writes unique keys beneath each `@session/{id}` prefix. Each call persists attacker-controlled values and operation-log entries. The default 30-day expiration bounds lifetime but not write rate or total live data, so an attacker can fill database storage and indexes or exhaust the in-memory provider.
- **Evidence:** The frontend command and attacker-controlled item array are declared at `src/ActualLab.Fusion.Ext.Contracts/Extensions/ISandboxedKeyValueStore.cs:11` and `src/ActualLab.Fusion.Ext.Contracts/Extensions/ISandboxedKeyValueStore.cs:34`. `GetKeyChecker` calls `Auth.GetUser` but still constructs a session-prefix checker when that result is null at `src/ActualLab.Fusion.Ext.Services/Extensions/Services/SandboxedKeyValueStore.cs:110`; its only default resource restriction is a 30-day expiry at `src/ActualLab.Fusion.Ext.Services/Extensions/Services/SandboxedKeyValueStore.cs:24`. `Set` allocates an array sized directly from the request and forwards every accepted item at `src/ActualLab.Fusion.Ext.Services/Extensions/Services/SandboxedKeyValueStore.cs:46`. The database implementation adds every unique key and saves it at `src/ActualLab.Fusion.Ext.Services/Extensions/Services/DbKeyValueStore.cs:48`, while the entity's key and value columns have no model-level maximum at `src/ActualLab.Fusion.Ext.Services/Extensions/Services/DbKeyValue.cs:14`.
- **Fix:** Enforce server-side per-call item and byte limits plus per-session live-key and aggregate-byte quotas; cap individual key/value lengths at both validation and schema levels. Apply rate limiting to anonymous writes and make guest storage opt-in or substantially shorter-lived. Quota checks and writes must be atomic so concurrent calls cannot bypass the limits.

### F5. Public auth responses serialize stored identity secrets

- **Severity:** HIGH
- **Confidence:** CONFIRMED
- **Category:** info-leak
- **Location:** `src/ActualLab.Fusion.Ext.Contracts/Authentication/User.cs:41`, `src/ActualLab.Fusion.Ext.Contracts/Authentication/User.cs:100`, `src/ActualLab.Fusion.Ext.Services/Authentication/Services/DbUserConverter.cs:49`, `src/ActualLab.Fusion.Ext.Services/Authentication/Services/DbAuthService.cs:176`
- **What:** The database converter places every identity's stored `Secret` into the `User` model, and the public `IAuth.GetUser(Session)` method returns that model unchanged. `User.JsonCompatibleIdentities` is explicitly serialized, while the existing `ToClientSideUser` masking method is never applied on either database or in-memory public return paths.
- **Why it matters / attack path:** An RPC client authenticated to an account calls `IAuth.GetUser` and receives every identity identifier and secret stored for that user. Applications are explicitly allowed to use this field for password hashes and may use it for other credential material; exposing it to a browser, mobile client, or stolen session turns a short-lived authenticated session into offline credential disclosure.
- **Evidence:** `DbUserConverter.UpdateModel` maps `ui.Secret` into `User.Identities` at `src/ActualLab.Fusion.Ext.Services/Authentication/Services/DbUserConverter.cs:49`. `JsonCompatibleIdentities` converts those exact map values to the serialized representation at `src/ActualLab.Fusion.Ext.Contracts/Authentication/User.cs:41`. The type already provides `ToClientSideUser`, which replaces identities with hidden placeholders at `src/ActualLab.Fusion.Ext.Contracts/Authentication/User.cs:100`, but `DbAuthService.GetUser(Session)` returns the unmasked `user` at `src/ActualLab.Fusion.Ext.Services/Authentication/Services/DbAuthService.cs:185`; `InMemoryAuthService` does the same at `src/ActualLab.Fusion.Ext.Services/Authentication/Services/InMemoryAuthService.cs:164`.
- **Fix:** Apply `ToClientSideUser()` to every result of the frontend `IAuth.GetUser(Session)` contract, while retaining an unmasked model only behind `IAuthBackend`. Prefer a separate client DTO that has no secret-valued property, and add serializer/RPC tests asserting that a nonempty stored secret and raw identity ID never appear in the client response.

### F6. One transient Redis subscription failure permanently wedges a subscriber

- **Severity:** MEDIUM
- **Confidence:** CONFIRMED
- **Category:** logic
- **Location:** `src/ActualLab.Redis/RedisSubBase.cs:22`, `src/ActualLab.Redis/RedisSubBase.cs:65`, `src/ActualLab.Redis/RedisQueue.cs:52`, `src/ActualLab.Redis/RedisQueue.cs:126`
- **What:** `RedisSubBase.Subscribe` caches its first subscription task forever, including when that task faults or times out. Every later call returns the same failed task, so the subscriber cannot recover after Redis connectivity returns.
- **Why it matters / attack path:** If Redis is unavailable for the first five seconds of a `RedisQueue` dequeue, `EnqueueSub.Subscribe()` times out. All future dequeues on that queue instance fail immediately at the same await even after the connector has recovered, permanently breaking queue consumption until the owning service is recreated. The same failure mode affects other long-lived `RedisSubBase` users that retry `Subscribe` on the same instance.
- **Evidence:** `WhenSubscribed` is a single cached task at `src/ActualLab.Redis/RedisSubBase.cs:22`. `Subscribe` returns it whenever non-null at `src/ActualLab.Redis/RedisSubBase.cs:67`, and the task created at `src/ActualLab.Redis/RedisSubBase.cs:71` can throw a timeout at `src/ActualLab.Redis/RedisSubBase.cs:82` without any code clearing the field. Both queue variants await that method before doing any list work at `src/ActualLab.Redis/RedisQueue.cs:54` and `src/ActualLab.Redis/RedisQueue.cs:128`.
- **Fix:** Use a retry-safe subscription state machine. On failure, atomically clear the cached task if it is still the current attempt, undo any partial subscription, and allow a later call to create a new attempt; coordinate this with disposal to prevent resubscription after stop. Add a test where the first subscription times out, Redis recovers, and a second dequeue succeeds on the same queue instance.
