### F1. Backend-command marker namespace mismatch bypasses backend-peer authorization

- **Severity:** CRITICAL
- **Confidence:** CONFIRMED
- **Category:** auth-bypass
- **Location:** `src/ActualLab.CommandR/Commands/IBackendCommand.cs:1`, `src/ActualLab.Rpc/Configuration/RpcMethodDef.cs:19`, `src/ActualLab.Rpc/Configuration/RpcMethodDef.Static.cs:33`, `src/ActualLab.Rpc/Infrastructure/RpcInboundContext.cs:47`, `src/ActualLab.Fusion.Ext.Services/Extensions/IKeyValueStore.cs:10`
- **What:** `IBackendCommand` is actually named `ActualLab.CommandR.Commands.IBackendCommand`, but RPC looks for `ActualLab.CommandR.IBackendCommand`. Consequently, command methods whose service itself is not backend-only are never marked `RpcMethodDef.IsBackend`, so the only backend-peer gate is skipped.
- **Why it matters / attack path:** A normal API peer can send an RPC call to a non-backend command service with a command implementing `IBackendCommand`. RPC correctly recognizes the root `ICommand`, classifies the call as a command, fails only the backend-marker test, and lets `RpcInboundCommandHandler` execute it through `ICommander`. The shipped `IKeyValueStore` is registered as an ordinary compute service and exposes `Set` and `Remove`; its command records implement `IBackendCommand`, so an unauthorized API peer can modify or delete arbitrary key-value-store entries by supplying shard/key data.
- **Evidence:** The marker is declared under `namespace ActualLab.CommandR.Commands` and as `public interface IBackendCommand : ICommand` (`src/ActualLab.CommandR/Commands/IBackendCommand.cs:1`, `src/ActualLab.CommandR/Commands/IBackendCommand.cs:13`). The classifier instead sets `BackendCommandInterfaceFullName` to `"ActualLab.CommandR.IBackendCommand"` (`src/ActualLab.Rpc/Configuration/RpcMethodDef.cs:19`) and compares that string to each interface's exact `FullName` (`src/ActualLab.Rpc/Configuration/RpcMethodDef.Static.cs:33`, `src/ActualLab.Rpc/Configuration/RpcMethodDef.Static.cs:38`). That failed result feeds `IsBackend = service.IsBackend || isBackend` (`src/ActualLab.Rpc/Configuration/RpcMethodDef.cs:105`), while inbound authorization rejects only when `MethodDef.IsBackend` is true (`src/ActualLab.Rpc/Infrastructure/RpcInboundContext.cs:47`). `IKeyValueStore` exposes command handlers `Set` and `Remove` (`src/ActualLab.Fusion.Ext.Services/Extensions/IKeyValueStore.cs:10`, `src/ActualLab.Fusion.Ext.Services/Extensions/IKeyValueStore.cs:12`); both records implement `IBackendCommand` (`src/ActualLab.Fusion.Ext.Services/Extensions/IKeyValueStore.cs:36`, `src/ActualLab.Fusion.Ext.Services/Extensions/IKeyValueStore.cs:46`), and the DB-backed registration uses the ordinary `fusion.AddService<IKeyValueStore, ...>()` path (`src/ActualLab.Fusion.Ext.Services/Extensions/FusionBuilderExt.cs:66`). Finally, the command middleware accepts every command by default and invokes the command context (`src/ActualLab.CommandR/Rpc/RpcInboundCommandHandler.cs:14`, `src/ActualLab.CommandR/Rpc/RpcInboundCommandHandler.cs:35`).
- **Fix:** Change the backend marker name to `ActualLab.CommandR.Commands.IBackendCommand` (prefer deriving it from a build-time-shared constant or adding a startup assertion so namespace moves cannot silently disable authorization). Add an integration test that invokes an `IBackendCommand` on a non-backend service over an API peer and asserts NotFound/rejection, plus a direct unit test that `RpcMethodDef.IsCommandType(typeof(KeyValueStore_Set), out isBackend)` sets both values to true. A defense-in-depth check in CommandR's inbound handler should reject `IBackendCommand` when `RpcInboundContext.Current.Peer.Ref.IsBackend` is false.

### F2. Wire-supplied `TypeRef` names reach an unbounded process-wide cache before call correlation

- **Severity:** HIGH
- **Confidence:** PLAUSIBLE
- **Category:** dos
- **Location:** `src/ActualLab.Core/Reflection/TypeRef.cs:31`, `src/ActualLab.Core/Reflection/TypeRef.cs:97`, `src/ActualLab.Core/Serialization/ExceptionInfo.cs:99`, `src/ActualLab.Rpc/Infrastructure/RpcSystemCalls.cs:95`
- **What:** `TypeRef.Resolve` caches every successfully resolved raw assembly-qualified-name string forever and deliberately does not retain failures. The cache key is the non-canonical, attacker-supplied string, not the resolved `Type`.
- **Why it matters / attack path:** Any peer can send a `$sys.Error` frame containing an attacker-chosen `ExceptionInfo.TypeRef` and an unrelated/nonexistent call id. `RpcSystemCalls.Error` constructs the exception, and therefore resolves the type name, before it looks up the related outbound call. Repeated valid textual variants that resolve to loaded types (for example assembly-name casing, optional qualification, and tolerated whitespace variants) create permanent distinct entries; repeated invalid names force fresh `Type.GetType`/assembly-binding work because failures are removed. This gives a pre-authenticated peer a process-lifetime memory/CPU amplification path. The cache-growth and pre-correlation reachability are confirmed from source; confidence is PLAUSIBLE because the request volume needed for practical exhaustion and the accepted-name-variant set were not measured in a repro.
- **Evidence:** `ResolveCache` is a static unbounded `ConcurrentDictionary<string, Type?>` (`src/ActualLab.Core/Reflection/TypeRef.cs:31`). `Resolve` uses the complete input string as its key, calls `Type.GetType`, retains successful results, and removes failures (`src/ActualLab.Core/Reflection/TypeRef.cs:97`, `src/ActualLab.Core/Reflection/TypeRef.cs:99`, `src/ActualLab.Core/Reflection/TypeRef.cs:101`). Remote `ExceptionInfo.ToException` calls `TypeRef.TryResolve()` before checking assignability (`src/ActualLab.Core/Serialization/ExceptionInfo.cs:99`, `src/ActualLab.Core/Serialization/ExceptionInfo.cs:101`). Most importantly, `$sys.Error` calls `error.ToException()` at line 100 and only afterwards performs `peer.OutboundCalls.Get(outboundCallId)` at line 103 (`src/ActualLab.Rpc/Infrastructure/RpcSystemCalls.cs:95`, `src/ActualLab.Rpc/Infrastructure/RpcSystemCalls.cs:100`).
- **Fix:** Reject uncorrelated `$sys.Error` messages before converting `ExceptionInfo`. Put a strict length limit on wire-supplied type names and restrict remote exception types to an explicit safe mapping. Remove the raw-string process-wide cache from the untrusted resolution path, or replace it with a small bounded cache that canonicalizes successful results and bounds negative entries/binder work.

### F3. Async scoped-service calls never perform asynchronous scope disposal

- **Severity:** MEDIUM
- **Confidence:** CONFIRMED
- **Category:** leak
- **Location:** `src/ActualLab.Interception/Interceptors/ScopedServiceInterceptor.cs:38`
- **What:** For an async intercepted method, `ScopedServiceInterceptor` creates an `IServiceScope` and attaches a fire-and-forget continuation that casts it only to `IDisposable`. It never calls or awaits `IAsyncDisposable.DisposeAsync`.
- **Why it matters / attack path:** `ScopedServiceInterceptor` is specifically usable as an RPC service resolver, so every remotely invoked async method can create this scope. If the scoped service or any dependency is async-disposable-only, Microsoft DI's synchronous scope disposal throws instead of running its cleanup; that exception belongs to the discarded continuation, while the RPC task has already completed. Repeated calls can leave sockets, streams, pooled connections, or other asynchronous resources unclosed and eventually break the service.
- **Evidence:** The async path creates the scope and invokes the service at `src/ActualLab.Interception/Interceptors/ScopedServiceInterceptor.cs:38` through `src/ActualLab.Interception/Interceptors/ScopedServiceInterceptor.cs:41`. Cleanup is `_ = task.ContinueWith(...)`, and the callback performs only `(scope1 as IDisposable)?.Dispose()` (`src/ActualLab.Interception/Interceptors/ScopedServiceInterceptor.cs:42`, `src/ActualLab.Interception/Interceptors/ScopedServiceInterceptor.cs:43`). The continuation task is discarded and the original task/`ValueTask` is returned (`src/ActualLab.Interception/Interceptors/ScopedServiceInterceptor.cs:46`).
- **Fix:** Return an async wrapper task that awaits the intercepted operation and then awaits scope disposal in `finally` (using `CreateAsyncScope`/`IAsyncDisposable` where available, with `IDisposable` fallback). The task exposed to the caller must include cleanup completion and cleanup failures; do not place disposal in an unobserved continuation.

### F4. “Thread-safe” cryptographic integer generators race on their shared output buffer

- **Severity:** MEDIUM
- **Confidence:** CONFIRMED
- **Category:** race
- **Location:** `src/ActualLab.Core/Generators/RandomInt32Generator.cs:11`, `src/ActualLab.Core/Generators/RandomInt64Generator.cs:11`
- **What:** `RandomInt32Generator` and `RandomInt64Generator` lock only while filling a shared byte array, then read that same array after releasing the lock. A second caller can overwrite the array between fill and read.
- **Why it matters / attack path:** Under concurrency, caller A can fill and release the lock, caller B can fill and read, and then caller A can read B's bytes. Both callers return the same value with ordinary scheduling probability instead of the advertised cryptographic collision probability; reads can also observe a buffer while another fill is in progress. Consumers using these explicitly “cryptographically random” generators for nonces, randomized identifiers, seeds, or sharding decisions therefore receive correlated or duplicated outputs.
- **Evidence:** The classes describe themselves as thread-safe cryptographic random generators (`src/ActualLab.Core/Generators/RandomInt32Generator.cs:6`, `src/ActualLab.Core/Generators/RandomInt32Generator.cs:8`, `src/ActualLab.Core/Generators/RandomInt64Generator.cs:6`, `src/ActualLab.Core/Generators/RandomInt64Generator.cs:8`). Both store output in an instance field (`src/ActualLab.Core/Generators/RandomInt32Generator.cs:11`, `src/ActualLab.Core/Generators/RandomInt64Generator.cs:11`), protect only `GetBytes` (`src/ActualLab.Core/Generators/RandomInt32Generator.cs:16`, `src/ActualLab.Core/Generators/RandomInt64Generator.cs:16`), and convert/read `_buffer` after the critical section (`src/ActualLab.Core/Generators/RandomInt32Generator.cs:18`, `src/ActualLab.Core/Generators/RandomInt64Generator.cs:19`).
- **Fix:** Use a per-call local buffer (prefer a stack-allocated span on supported targets) and let `RandomNumberGenerator` handle concurrent calls, or keep both the fill and integer read inside the same lock. Add a high-contention test with an instrumented RNG that forces the fill/read interleaving.

### F5. `LazySlim` publishes initialization through a non-volatile double check

- **Severity:** MEDIUM
- **Confidence:** PLAUSIBLE
- **Category:** race
- **Location:** `src/ActualLab.Core/LazySlim.cs:53`, `src/ActualLab.Core/LazySlim.cs:59`, `src/ActualLab.Core/Collections/ConcurrentDictionaryExt.cs:12`, `src/ActualLab.Interception/ArgumentList.cs:17`
- **What:** All three `LazySlim` variants use `_factory == null` as the lock-free initialized marker, but `_factory` is neither volatile nor accessed through `Volatile.Read/Write`. The initialized value is written under a lock and then `_factory` is cleared, while fast-path readers acquire neither that lock nor an acquire fence.
- **Why it matters / attack path:** The C# memory model does not establish a happens-before edge from the initializing thread to a reader that merely observes the ordinary `_factory` field. On weakly ordered architectures/JITs, a racing reader can observe the null marker yet return the backing field's default/stale value. This primitive backs concurrent-dictionary initialization throughout the framework, including `ArgumentList` invoker generation; concurrent first RPC invocations of one method can therefore receive a null/stale invoker and fail. The missing synchronization is confirmed, but confidence is PLAUSIBLE because the stale-publication outcome is architecture/timing dependent and was not reproduced.
- **Evidence:** `_factory` is a plain `Delegate?` (`src/ActualLab.Core/LazySlim.cs:53`); the fast path returns the value immediately when that field is null (`src/ActualLab.Core/LazySlim.cs:59`, `src/ActualLab.Core/LazySlim.cs:60`), while initialization writes the value and then sets `_factory = null` (`src/ActualLab.Core/LazySlim.cs:66`, `src/ActualLab.Core/LazySlim.cs:74`). The same pattern is repeated in the one- and two-argument variants (`src/ActualLab.Core/LazySlim.cs:107`, `src/ActualLab.Core/LazySlim.cs:115`, `src/ActualLab.Core/LazySlim.cs:129`, `src/ActualLab.Core/LazySlim.cs:166`, `src/ActualLab.Core/LazySlim.cs:175`, `src/ActualLab.Core/LazySlim.cs:189`). `ConcurrentDictionaryExt.GetOrAdd` immediately returns this `.Value` (`src/ActualLab.Core/Collections/ConcurrentDictionaryExt.cs:12`, `src/ActualLab.Core/Collections/ConcurrentDictionaryExt.cs:19`), and `ArgumentList` uses that shape for its shared invoker cache (`src/ActualLab.Interception/ArgumentList.cs:17`, `src/ActualLab.Interception/ArgumentList.cs:95`).
- **Fix:** Make publication explicit: use `Volatile.Read(ref _factory)` for both checks and `Volatile.Write(ref _factory, null)` only after storing the value (or make `_factory` volatile). Apply the same release/acquire protocol to every variant and add a stress test on ARM64.

### F6. Plugin handles leak async-disposable plugin instances

- **Severity:** MEDIUM
- **Confidence:** CONFIRMED
- **Category:** leak
- **Location:** `src/ActualLab.Plugins/Internal/PluginInstanceHandle.cs:8`, `src/ActualLab.Plugins/Internal/PluginInstanceHandle.cs:55`, `src/ActualLab.Plugins/PluginHostBuilder.cs:27`
- **What:** `IPluginInstanceHandle` and its implementation support only synchronous disposal. Cleanup casts the plugin instance only to `IDisposable`, so a plugin implementing only `IAsyncDisposable` is never cleaned up; it also evaluates `Lazy.Value` during disposal, which can instantiate an otherwise unused directly-resolved handle just to dispose it.
- **Why it matters / attack path:** Plugin instances are created by `PluginFactory` and owned only through the singleton handle registered in DI. When a valid async-only plugin opens streams, sockets, timers, or other asynchronously cleaned resources, disposing the plugin host disposes the handle synchronously and silently skips the plugin's cleanup, leaking those resources across host lifecycles.
- **Evidence:** The ownership interface extends only `IDisposable` (`src/ActualLab.Plugins/Internal/PluginInstanceHandle.cs:8`), and the open generic handle is registered as a singleton service (`src/ActualLab.Plugins/PluginHostBuilder.cs:27`). Disposal nulls the lazy, forces `lazyInstance.Value`, casts only to `IDisposable`, and invokes only `Dispose` (`src/ActualLab.Plugins/Internal/PluginInstanceHandle.cs:55`, `src/ActualLab.Plugins/Internal/PluginInstanceHandle.cs:57`, `src/ActualLab.Plugins/Internal/PluginInstanceHandle.cs:58`).
- **Fix:** Make handles implement `IAsyncDisposable`, avoid evaluating the lazy when `IsValueCreated` is false, and in `DisposeAsync` prefer the plugin's `IAsyncDisposable.DisposeAsync` with `IDisposable.Dispose` fallback. Ensure the host/provider async-disposal path awaits handle cleanup.

### F7. `PluginHost.DisposeAsync` silently skips sync-only custom providers

- **Severity:** MEDIUM
- **Confidence:** CONFIRMED
- **Category:** leak
- **Location:** `src/ActualLab.Plugins/PluginHost.cs:24`, `src/ActualLab.Plugins/PluginHostBuilder.cs:12`
- **What:** `PluginHost.DisposeAsync` returns a completed `ValueTask` when its wrapped provider does not implement `IAsyncDisposable`, even if that provider implements `IDisposable`. This differs from the builder's own failure cleanup, which correctly falls back to synchronous disposal.
- **Why it matters / attack path:** `PluginHostBuilder` explicitly supports an arbitrary custom `IServiceProvider` factory. A caller using the host's advertised `IAsyncDisposable` contract (`await using`) with a sync-only provider receives apparent successful cleanup, but the provider and all of its plugin singletons/scopes remain undisposed.
- **Evidence:** A custom provider factory may return any `IServiceProvider` (`src/ActualLab.Plugins/PluginHostBuilder.cs:12`, `src/ActualLab.Plugins/PluginHostBuilder.cs:48`). The host calls `DisposeAsync` only for `IAsyncDisposable` and otherwise returns `default` (`src/ActualLab.Plugins/PluginHost.cs:24`, `src/ActualLab.Plugins/PluginHost.cs:27`). In contrast, `BuildAsync`'s exception path explicitly uses `IAsyncDisposable` and then `else if (services is IDisposable)` (`src/ActualLab.Plugins/PluginHostBuilder.cs:56`, `src/ActualLab.Plugins/PluginHostBuilder.cs:58`).
- **Fix:** Implement `PluginHost.DisposeAsync` with the same async-first, synchronous-fallback logic as `BuildAsync`. Add coverage using a custom provider that implements only `IDisposable` and assert that `await host.DisposeAsync()` disposes it exactly once.
