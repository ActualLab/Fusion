### F1. WebSocket endpoints accept credentialed connections from any origin

- **Severity:** HIGH
- **Confidence:** CONFIRMED
- **Category:** auth-bypass
- **Location:** `src/ActualLab.Rpc.Server/RpcWebSocketServer.cs:33`, `src/ActualLab.Rpc.Server.NetFx/RpcWebSocketServer.cs:31`, `src/ActualLab.Fusion.Server/Rpc/RpcPeerOptionsExt.cs:34`
- **What:** Both server implementations accept a WebSocket based only on whether the host exposes an upgrade feature; neither checks the request's `Origin` against an allowlist. The Fusion connection factory then binds the connection to the session cookie automatically.
- **Why it matters / attack path:** A page on an attacker-controlled origin can open the RPC WebSocket directly because WebSockets are not protected by CORS. When the browser is willing to send the target cookie—concretely, from a malicious same-site sibling origin under the default `SameSite=Lax` cookie, or cross-site when an application configures `SameSite=None`—the connection is bound to the victim's Fusion session. The attacker can then speak the public RPC protocol and invoke frontend RPC methods as that session without learning the HttpOnly cookie.
- **Evidence:** The ASP.NET Core handler checks only `context.WebSockets.IsWebSocketRequest` and proceeds to `AcceptWebSocketAsync` (`src/ActualLab.Rpc.Server/RpcWebSocketServer.cs:33`, `src/ActualLab.Rpc.Server/RpcWebSocketServer.cs:79`); the OWIN handler similarly checks only for `"websocket.Accept"` (`src/ActualLab.Rpc.Server.NetFx/RpcWebSocketServer.cs:31`). No P4 source reads `Origin`. Fusion falls back to `sessionMiddleware.GetSession(httpContext)` and creates a `SessionBoundRpcConnection` from that cookie (`src/ActualLab.Fusion.Server/Rpc/RpcPeerOptionsExt.cs:34`).
- **Fix:** Add a configurable origin predicate to both WebSocket server options, default it to strict same-origin matching, and reject disallowed or missing origins before peer creation and upgrade. Keep an explicit opt-out for non-browser/native clients, and update all samples to configure ASP.NET Core `WebSocketOptions.AllowedOrigins` as defense in depth.

### F2. Arbitrary client IDs create long-lived peers before authentication or handshake

- **Severity:** HIGH
- **Confidence:** CONFIRMED
- **Category:** dos
- **Location:** `src/ActualLab.Rpc.Server/RpcWebSocketServerDefaultDelegates.cs:29`, `src/ActualLab.Rpc.Server/RpcWebSocketServer.cs:62`, `src/ActualLab.Rpc.Server/RpcHttpServer.cs:57`, `src/ActualLab.Rpc.Server.NetFx/RpcWebSocketServer.cs:45`
- **What:** The server accepts any query-string `clientId` and uses it to allocate and start a distinct `RpcServerPeer` before authentication and before the RPC handshake. There is no client-ID format check, admission limit, or per-source peer quota in the hosting layer.
- **Why it matters / attack path:** An unauthenticated attacker repeatedly sends valid WebSocket upgrades (or HTTP/2 RPC requests) with a fresh `clientId` and a supported serialization format, then aborts before or just after handshake. Every unique value bypasses peer reuse and leaves a peer/task in the hub; after disconnection, a server peer waits at least three minutes for reconnection. A sustained low-cost request stream therefore grows the peer dictionary and live async state fast enough to exhaust server memory.
- **Evidence:** The default ref factory copies the attacker value directly into `RpcRef.NewServer(clientId, ...)` (`src/ActualLab.Rpc.Server/RpcWebSocketServerDefaultDelegates.cs:29`), and both transports call `Hub.GetServerPeer(rpcRef)` before establishing a connection (`src/ActualLab.Rpc.Server/RpcWebSocketServer.cs:62`, `src/ActualLab.Rpc.Server/RpcHttpServer.cs:57`; OWIN does the same at `src/ActualLab.Rpc.Server.NetFx/RpcWebSocketServer.cs:45`). Supporting lifecycle code inserts and starts every new peer (`src/ActualLab.Rpc/RpcHub.cs:137`) and clamps the disconnected server-peer wait to 3–15 minutes (`src/ActualLab.Rpc/Configuration/Options/RpcPeerOptions.cs:54`).
- **Fix:** Validate client IDs against the fixed-length Base64URL form generated by Fusion, authenticate and apply origin policy before allocation, and impose global/per-IP limits on pending and retained server peers. Remove never-handshaken peers immediately on request abort or handshake failure rather than giving them the normal reconnect grace period.

### F3. RestEase buffers an unbounded hostile 500 response

- **Severity:** HIGH
- **Confidence:** CONFIRMED
- **Category:** dos
- **Location:** `src/ActualLab.RestEase/Internal/RestEaseHttpMessageHandler.cs:31`, `src/ActualLab.RestEase/Internal/RestEaseHttpMessageHandler.cs:33`, `src/ActualLab.RestEase/RestEaseBuilder.cs:35`
- **What:** Every HTTP 500 response handled by `RestEaseHttpMessageHandler` is read completely into a string with no byte limit before its content type or error shape is validated. The read also does not receive the caller's cancellation token.
- **Why it matters / attack path:** A compromised or attacker-controlled HTTP server returns status 500 with a huge or indefinitely streamed body. The client eagerly accumulates the entire body and then may parse it again as JSON, allowing one response to consume memory until the client process is killed; `AddRestEase` makes this handler available through the application's `IHttpClientFactory` pipeline.
- **Evidence:** `DeserializeError` immediately executes `await response.Content.ReadAsStringAsync()` (`src/ActualLab.RestEase/Internal/RestEaseHttpMessageHandler.cs:33`) and only afterward checks `Content-Type` and parses the complete string (`src/ActualLab.RestEase/Internal/RestEaseHttpMessageHandler.cs:34`). No maximum length or bounded stream is present.
- **Fix:** Read at most a small configurable error-body limit (for example 64 KiB) from the response stream using the request cancellation token, abort/dispose on overflow, and return a generic truncated `RemoteException`. Apply JSON depth/size limits to the bounded payload.

### F4. Query-string RPC sessions bypass the registered session validator

- **Severity:** MEDIUM
- **Confidence:** CONFIRMED
- **Category:** auth-bypass
- **Location:** `src/ActualLab.Fusion.Server/Rpc/RpcPeerOptionsExt.cs:28`, `src/ActualLab.Fusion.Server/Rpc/RpcPeerOptionsExt.cs:31`, `src/ActualLab.Fusion.Server/Middlewares/SessionMiddleware.cs:89`
- **What:** A `session` supplied in the RPC URL takes precedence over the ambient cookie and is checked only with the structural `Session.IsValid()` predicate. The registered `ISessionValidator`, which the HTTP session middleware uses for policy validation, is never invoked for this path.
- **Why it matters / attack path:** A remote client supplies a syntactically valid session ID that an application's validator rejects—for example a revoked, expired, or tenant-ineligible session. The connection factory still creates a `SessionBoundRpcConnection`, and calls using `Session.Default` are rewritten to that rejected identity. Any session-scoped RPC method that assumes the connection boundary already enforced `ISessionValidator` is reached under a policy-invalid session.
- **Evidence:** The query branch constructs `new Session(sessionId)`, calls only `session1.IsValid()`, and immediately binds it (`src/ActualLab.Fusion.Server/Rpc/RpcPeerOptionsExt.cs:28`, `src/ActualLab.Fusion.Server/Rpc/RpcPeerOptionsExt.cs:31`). By contrast, the normal middleware explicitly awaits `SessionValidator.IsValidSession(...)` (`src/ActualLab.Fusion.Server/Middlewares/SessionMiddleware.cs:89`). `RpcDefaultSessionReplacer` then substitutes the bound session into inbound calls (`src/ActualLab.Fusion.Server/Rpc/RpcDefaultSessionReplacer.cs:35`).
- **Fix:** Make the server connection factory validate every query-supplied session with the scoped `ISessionValidator` before binding it, and reject the connection on failure. Prefer the already validated scoped `ISessionResolver` for cookie sessions, and consider disabling bearer query sessions unless explicitly configured.

### F5. Normal RPC logging records bearer session query parameters

- **Severity:** MEDIUM
- **Confidence:** CONFIRMED
- **Category:** info-leak
- **Location:** `src/ActualLab.Rpc.Server/RpcWebSocketServer.cs:25`, `src/ActualLab.Rpc.Server/RpcWebSocketServer.cs:61`, `src/ActualLab.Rpc.Server/RpcHttpServer.cs:25`, `src/ActualLab.Rpc.Server.NetFx/RpcWebSocketServer.cs:108`
- **What:** The ASP.NET Core servers build a request description containing the complete query string and log it at Information level for every accepted connection; error paths log it again. The NetFx error path also logs the raw query string.
- **Why it matters / attack path:** Fusion explicitly accepts the `session` query parameter as the session bound to an RPC connection. A legitimate token-bearing connection therefore copies its replayable session credential into routine server logs, where operators, support exports, log aggregation systems, or a later log compromise can expose it to a party that can impersonate the session.
- **Evidence:** `request.QueryString.ToString()` is embedded into the URI (`src/ActualLab.Rpc.Server/RpcWebSocketServer.cs:25`) and the resulting value is logged by `"Accepting RPC connection for {Request}"` (`src/ActualLab.Rpc.Server/RpcWebSocketServer.cs:61`); the HTTP/2 server has the same construction and log (`src/ActualLab.Rpc.Server/RpcHttpServer.cs:25`, `src/ActualLab.Rpc.Server/RpcHttpServer.cs:56`). Fusion consumes `query["session"]` as the bound session (`src/ActualLab.Fusion.Server/Rpc/RpcPeerOptionsExt.cs:28`), while NetFx logs `{Path}{Query}` on failure (`src/ActualLab.Rpc.Server.NetFx/RpcWebSocketServer.cs:108`).
- **Fix:** Never log raw RPC query strings. Log only the path and allowlisted non-secret metadata, and redact `session`, authorization tokens, signatures, and application-configured sensitive keys in every normal and exception path.

### F6. Default invalid-session recovery can permanently redirect-loop a client

- **Severity:** MEDIUM
- **Confidence:** CONFIRMED
- **Category:** logic
- **Location:** `src/ActualLab.Fusion.Server/Middlewares/SessionMiddleware.cs:32`, `src/ActualLab.Fusion.Server/Middlewares/SessionMiddleware.cs:36`, `src/ActualLab.Fusion.Server/Middlewares/SessionMiddleware.cs:98`
- **What:** The default invalid-session handler signs out ASP.NET authentication and redirects to the same URL, then requests middleware short-circuiting, but it neither deletes nor replaces the invalid `FusionAuth.SessionId` cookie. If no default sign-out scheme exists, the unconditional `SignOutAsync()` can throw instead.
- **Why it matters / attack path:** A user's session is force-revoked, expires under a custom validator, or carries a stale/malformed cookie. Every redirected request presents the same rejected Fusion cookie, takes the same short-circuit path, and receives another redirect, so the user cannot recover without manually deleting cookies. Fusion applications without ASP.NET authentication can instead turn the same invalid cookie into a persistent 500 response.
- **Evidence:** The default handler calls `SignOutAsync`, redirects to `GetEncodedPathAndQuery()`, and returns `true` (`src/ActualLab.Fusion.Server/Middlewares/SessionMiddleware.cs:32`). On `true`, `InvokeAsync` returns before downstream processing (`src/ActualLab.Fusion.Server/Middlewares/SessionMiddleware.cs:64`), and `GetOrCreateSession` returns before the only cookie-writing block at lines 108–112 (`src/ActualLab.Fusion.Server/Middlewares/SessionMiddleware.cs:98`).
- **Fix:** Expire or rotate the Fusion session cookie before redirecting, and issue a fresh session on the next request. Do not unconditionally call the default authentication sign-out operation when no scheme is configured; make that behavior explicit/configurable and add a two-request regression test for recovery.

### F7. JsonifyErrors exposes internal exception types and messages to HTTP callers

- **Severity:** MEDIUM
- **Confidence:** CONFIRMED
- **Category:** info-leak
- **Location:** `src/ActualLab.Fusion.Server/JsonifyErrorsAttribute.cs:21`, `src/ActualLab.Fusion.Server/JsonifyErrorsAttribute.cs:23`, `src/ActualLab.Fusion.Server.NetFx/JsonifyErrorsAttribute.cs:25`
- **What:** Both exception filters serialize the concrete exception type and raw message into every HTTP 500 response. There is no environment check, authorization check, or allowlist of client-safe exception types/messages.
- **Why it matters / attack path:** A remote caller invokes a controller protected by this filter and triggers an exception whose message contains database/provider details, validation internals, paths, identifiers, or other sensitive context. The caller receives that message plus the assembly-qualified exception type, providing information that normal production error handling would keep server-side.
- **Evidence:** ASP.NET Core executes `serializer.Write(exception.ToExceptionInfo())` and returns the result as `application/json` (`src/ActualLab.Fusion.Server/JsonifyErrorsAttribute.cs:21`, `src/ActualLab.Fusion.Server/JsonifyErrorsAttribute.cs:23`). NetFx performs the same serialization into `StringContent` (`src/ActualLab.Fusion.Server.NetFx/JsonifyErrorsAttribute.cs:25`). `ExceptionInfo` captures `exception.GetType()` and `exception.Message` (`src/ActualLab.Core/Serialization/ExceptionInfo.cs:47`).
- **Fix:** Return a stable public error code, generic message, and correlation ID by default. Preserve details only for explicitly allowlisted public exceptions or development mode, and keep the complete exception exclusively in server logs.

### F8. NetFx default-session filtering resolves the root provider instead of the request scope

- **Severity:** MEDIUM
- **Confidence:** CONFIRMED
- **Category:** logic
- **Location:** `src/ActualLab.Fusion.Server.NetFx/HttpContextExt.cs:26`, `src/ActualLab.Fusion.Server.NetFx/UseDefaultSessionAttribute.cs:20`
- **What:** `UseDefaultSessionAttribute` resolves `ISessionResolver` from `Configuration.DependencyResolver`, the root Web API provider, rather than from the current request's dependency scope. Fusion registers `ISessionResolver` as scoped and initializes the request instance.
- **Why it matters / attack path:** A normal POST action carrying an `ISessionCommand` with `Session.Default` enters the filter, but the root resolver is uninitialized, so `command.UseDefaultSession` throws instead of substituting the request session. With a custom mutable root resolver, the alternative failure is worse: requests can share or reuse another request's session.
- **Evidence:** `GetAppServices` returns `httpContext.RequestContext.Configuration.DependencyResolver` (`src/ActualLab.Fusion.Server.NetFx/HttpContextExt.cs:26`), and the filter obtains `ISessionResolver` from it (`src/ActualLab.Fusion.Server.NetFx/UseDefaultSessionAttribute.cs:20`). Fusion's standard registration is scoped (`src/ActualLab.Fusion/FusionBuilder.cs:114`), while an unset `SessionResolver.Session` throws and mutation requires a scoped provider (`src/ActualLab.Fusion/Session/SessionResolver.cs:32`).
- **Fix:** Resolve services from `actionContext.Request.GetDependencyScope()` (or the equivalent request-scoped resolver) and fail closed if no request session was initialized. Add concurrent two-request tests proving that default-session replacement uses the correct scope.

### F9. AddRestEase changes 500 handling for every HttpClientFactory client

- **Severity:** MEDIUM
- **Confidence:** CONFIRMED
- **Category:** logic
- **Location:** `src/ActualLab.RestEase/RestEaseBuilder.cs:35`, `src/ActualLab.RestEase/RestEaseBuilder.cs:36`, `src/ActualLab.RestEase/Internal/RestEaseHttpMessageHandlerBuilderFilter.cs:12`
- **What:** `AddRestEase` registers an `IHttpMessageHandlerBuilderFilter`, which runs for every named and typed client created by the application's `IHttpClientFactory`, not only clients added through `RestEaseBuilder.AddClient`. The filter inserts the Fusion-specific 500 translator unconditionally.
- **Why it matters / attack path:** An application combines RestEase with an unrelated HTTP client whose contract requires inspecting or returning a 500 response. Merely registering RestEase causes that unrelated response to be consumed, disposed, and replaced with a `RemoteException`, breaking retry, status-code, and body-handling logic throughout the application.
- **Evidence:** `AddRestEase` calls `services.AddHttpClient()` and globally registers `RestEaseHttpMessageHandlerBuilderFilter` as an `IHttpMessageHandlerBuilderFilter` (`src/ActualLab.RestEase/RestEaseBuilder.cs:35`). Its `Configure` method has no client-name/type condition and inserts the handler at index zero for every builder (`src/ActualLab.RestEase/Internal/RestEaseHttpMessageHandlerBuilderFilter.cs:12`); that handler intercepts and disposes every 500 response (`src/ActualLab.RestEase/Internal/RestEaseHttpMessageHandler.cs:18`).
- **Fix:** Attach `RestEaseHttpMessageHandler` only to the named clients created by `RestEaseBuilder.AddClient`, using per-client `IHttpClientBuilder` configuration or a strictly maintained set of RestEase client names. Leave unrelated factory clients untouched.

### F10. NetFx plain-text formatter buffers and duplicates the entire request body

- **Severity:** MEDIUM
- **Confidence:** PLAUSIBLE
- **Category:** dos
- **Location:** `src/ActualLab.Fusion.Server.NetFx/TextMediaTypeFormatter.cs:21`, `src/ActualLab.Fusion.Server.NetFx/TextMediaTypeFormatter.cs:23`, `src/ActualLab.Fusion.Server.NetFx/TextMediaTypeFormatter.cs:25`
- **What:** The NetFx formatter copies the complete request stream into an unbounded `MemoryStream` and then calls `ToArray`, temporarily duplicating the full payload, with no local size limit or cancellation path.
- **Why it matters / attack path:** In a deployment that registers this formatter and exposes a string-body action, an unauthenticated caller can send large or chunked `text/plain` bodies. Concurrent requests can consume multiple times their wire size in managed memory and pressure the process into sustained GC or OOM; the exact severity depends on IIS/proxy request-size limits, which are outside the repository and therefore unverified.
- **Evidence:** `ReadFromStreamAsync` creates an unrestricted `MemoryStream`, awaits `readStream.CopyToAsync(memoryStream)`, and converts it with `memoryStream.ToArray()` (`src/ActualLab.Fusion.Server.NetFx/TextMediaTypeFormatter.cs:21`). No `Content-Length` check, bounded copy, or maximum is present.
- **Fix:** Add a configurable maximum text-body size, reject oversized declared or streamed bodies with 413, and decode through a bounded/cancellable stream path without the extra `ToArray` copy. Document the required matching IIS/reverse-proxy limit.
